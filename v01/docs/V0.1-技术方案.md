# AI PPT Sys V0.1 总体技术方案

本文依据《AI PPT Sys — V0.1 总体开发任务书》编制，作为后续开发的实施依据。旧仓库 `ai-acadmic-ppt-sys` 中的代码暂时冻结，只作参考与零件复用，新版本不要求兼容旧架构。

完成标准只有一条：系统能从一句模糊的自然语言出发，自主完成内容规划、素材检索、语义匹配、页面设计和 PowerPoint 生成，并交付一份可打开、基本可编辑、可检查的 PPTX。不以模块数量或 Agent 数量衡量进度。

---

## 1. 总体结构

采用一条最短生产链，用磁盘上的明确契约连接各阶段，不用多 Agent 编排框架。

主链路：

```
用户一句话
  → A 制作计划 Production Plan
  → B 暂定页面规划 Provisional Slide Plan（含研究简报，不锁死主张和页序）
  → C 素材需求 Asset Requirements
  → D 素材获取 Asset Registry
  → 修订：主编根据真实素材改 Slide Plan，必要时回写 C 并补取 D
  → E 素材绑定 Slide Asset Mapping
  → F 页面视觉设计 Page Design + 预览
  → G 生成 PPTX
  → H 渲染、检查、必要修复
  → 最终 PPTX、预览、检查报告
```

只有一处回流：素材回来之后，主编可以改页、改表达、降级或拆页，并补取缺失素材。不允许把回流做成新的编排器或新的模块层。检索失败时，允许改查询、改表达，或改用合规的自绘元素；不得用假素材或占位图冒充已获取资源。

各阶段的输入、输出都落在当次运行的工作目录里，必须是真实、可打开、可单独检查的文件。上游的输出就是下游的输入，字段以本文契约为准。

## 2. 职责边界

系统里只有一个「主编」角色，对应任务书的阶段 A，以及素材返回后的改稿权。现有 APC 若沿用这个名字，就必须按这个边界重写，不再使用旧的 00–09 任务书和 `PPT_HANDOFF.json` 作为主合同。

### 2.1 主编（APC）该做

- 把用户原话编成 Production Plan：主题、用途、受众、语言、风格、约束。
- 用户没说清的信息可以做默认决策，但必须写入 `defaults_applied`，可供检查和推翻。
- 提出内容方向和检索要点，为每页写「这一页要讲清什么」，不写幻灯正文，不画成品图。
- 素材回来后拍板：改定主张和页序，拆页或合并，去掉素材支撑不住的表述，必要时更新素材需求。

主编的独立验收有两次，不依赖后面是否已经做出 PPT：

1. 只给一句话，检查它是否只交出计划和检索需求，有没有提前锁死页数、页序和已经写成结论的主张。
2. 再给一份真实或专门准备的素材包，检查它会不会根据素材改稿，会不会把无关素材塞进页面。

### 2.2 主编不该做

- 阶段 C 到 E：检索、下载、核源、绑定。
- 阶段 F：视觉设计和版式系统。
- 阶段 G：生成 PPTX。
- 阶段 H：渲染质检；它可以阅读检查结果并改内容计划，但不自己修版式。
- 第一次规划就把页数、页序和结论写死。
- 在编排器里只做校验，或自己去出成品 PPT。

### 2.3 其他阶段

| 阶段 | 职责 | 不该做 |
| --- | --- | --- |
| B 内容研究与页面规划 | 做必要检索与研究，给出叙事方向和暂定逐页目标 | 把暂定规划当成不可改的目录；把尚未被素材支撑的判断写成既定事实 |
| C 素材需求分析 | 按「这一页要说明什么」列出具体素材需求 | 无目的地堆积素材类型 |
| D 素材检索与获取 | 按需求检索、下载、登记来源与使用条件 | 用无关素材凑数；用模拟数据冒充外部资源 |
| E 语义绑定 | 把合格素材接到具体页面和用途上 | 因为已经下载就硬塞进不相关的页 |
| F 页面视觉编排 | 按真实内容和真实素材做版式，并出预览 | 在素材尚未绑定前回填设计；把整页做成一张不可编辑的图 |
| G PPTX 制作 | 写成可编辑的 PowerPoint | 用整页截图冒充幻灯片 |
| H 检查与修复 | 真实渲染并检查溢出、遮挡、缺图、错配等，能修则修并复验 | 只做 JSON 字段校验就视为通过 |

阶段 B 是当前最容易走回旧路的一截。B 的第一次输出只能是 `provisional`。页数、页序和核心表述的定稿，发生在 D 之后的修订，而不是 B 刚结束时。

V0.1 不做全自动学术审稿，也不沿用旧的 READY / BLOCKED 作为唯一门禁。第一版要保证素材真实、来源可追溯、和页面用途匹配；「看起来很好、其实站不住」的深度证据审查放到后续版本，不要塞回主编。

## 3. 数据契约

所有契约用 JSON，UTF-8，字段用 snake_case。每份文件含 `schema_version`（V0.1 为 `"0.1"`）和 `run_id`。ID 一经发出不得复用：页面 `S001` 起，素材需求 `A001` 起。

下面只列稳定字段。实现时可用 JSON Schema 或 Pydantic 做校验，但不要把契约再包一层平台格式。

### 3.1 Production Plan（A 输出，`production_plan.json`）

```json
{
  "schema_version": "0.1",
  "run_id": "uhi-20261120-001",
  "source_utterance": "帮我做一个城市热岛效应的 PPT。",
  "topic": "城市热岛效应",
  "purpose": "general_presentation",
  "audience": "general",
  "language": "zh-CN",
  "style": "clear_educational",
  "constraints": [],
  "defaults_applied": [
    {
      "field": "audience",
      "value": "general",
      "rationale": "用户未指定受众，按通用讲解处理"
    }
  ],
  "content_direction": "从现象、成因、影响和应对四条线索展开，避免过早给出单一城市的定论。",
  "open_questions": []
}
```

`purpose`、`audience`、`language`、`style` 允许使用受控词，同时保留原话摘要。没有依据就不得写死页数或时长。

### 3.2 Slide Plan（B 输出，修订后回写同一文件，`slide_plan.json`）

```json
{
  "schema_version": "0.1",
  "run_id": "uhi-20261120-001",
  "status": "provisional",
  "narrative": "先建立概念，再讲可观察的成因与影响，最后讨论应对，不预设结论性口号。",
  "pages": [
    {
      "page_id": "S001",
      "title": "什么是城市热岛",
      "goal": "让听众能把城市热岛和一般热浪区分开",
      "key_points": ["城区相对周边更热", "与短期热浪不是同一现象"],
      "content_summary": "用定义和对比说明现象本身。",
      "visual_intent": "一张对比示意，而不是装饰图",
      "asset_needs": ["需要一张可解释的对比图或简明数据"],
      "status": "provisional"
    }
  ],
  "revision_log": []
}
```

`status` 只取 `provisional` 或 `revised`。`key_points` 是这一页要讲清的点，不是已证实的论文主张。修订时必须追加 `revision_log`，说明改了什么、依据哪条素材。不得因「先要有目录」而把第一稿标成定稿。

### 3.3 Asset Requirements（C 输出，`asset_requirements.json`）

每条需求必须能指向页面和用途：

- `asset_id`、`page_ids`、`type`（`image` / `icon` / `diagram` / `chart_data` / `table` / `reference` / `statistic`）
- `purpose`：这件素材在页上具体完成什么
- `query_hints`：检索线索，不是唯一查询
- `priority`：`required` 或 `optional`
- `acceptance`：什么样算合格（相关、可合法使用、清晰可读等）

### 3.4 Asset Registry（D 输出，`asset_registry.json` + `assets/`）

每条登记对应一个实文件或一次明确失败：

- `asset_id`（对应需求）、`file_path`、`source_url`、`source_name`
- `license_or_terms`、`retrieved_at`
- `status`：`acquired` / `substituted` / `drawn` / `missing`
- `notes`：为何替换、为何自绘、为何缺失
- `checks`：相关性、可用性、格式、质量的简要结论

工作目录里必须能打开对应文件。`missing` 可以进入修订，不能假装成功。引用文献类素材至少登记来源和可核验标识（如 DOI）；V0.1 不要求吃进全文并做学术审稿，但不得编造条目。

### 3.5 Slide Asset Mapping（E 输出，`slide_asset_mapping.json`）

- `page_id`、`asset_id`、`usage`（这件素材在这页上干什么）
- `accepted`：是否真正支撑该页目标

未绑定的已下载素材必须留在登记里，标注「未使用」及原因，禁止为了用掉而塞进无关页。同一素材可复用到多页，但每页都要写用途。

### 3.6 Page Design（F 输出，`page_design.json` + `previews/`）

每页一份设计描述，至少包括：

- `page_id`、画布尺寸（V0.1 默认 13.333 英寸 × 7.5 英寸，16:9）
- 元素列表：`element_id`、`kind`（`title` / `body` / `bullet` / `image` / `shape` / `chart` / `caption` / `footer`）
- 位置与尺寸（英寸）、层级、对齐
- 文本内容、字体与字号；图片则指向已绑定素材路径
- 该页预览图路径

允许因真实素材比例或内容密度修改原规划，修改原因写入该页备注。F 不发明未绑定的新素材。

### 3.7 成品与质检（G / H 输出）

- `deck.pptx`：可打开，主体为原生文本、形状、图表，外部图以图片对象嵌入，不是整页截图拼贴。
- `render/`：每页预览图（如 PNG）。
- `qa_report.json`：逐页记录文字溢出、遮挡、缺图、布局异常、字体与比例、内容与素材不匹配；记录修复与复验结果。
- `run_report.json`：阶段是否成功、默认决策摘要、缺失素材、修订次数、失败原因。

## 4. 技术栈

选栈原则是能跑通生产，而不是搭平台。

| 用途 | 选择 | 依据 |
| --- | --- | --- |
| 语言与包管理 | Python 3.11+，`pyproject.toml` | 与旧仓库一致，便于复用零件 |
| 契约与校验 | Pydantic v2 | 字段约束清楚，测试好写 |
| 阶段串联 | 本仓库内的线性 Runner 和 CLI | 满足 A–H 即可，不引入 LangGraph 或多 Agent 框架 |
| 主编与规划 | 可配置的大模型接口（OpenAI 兼容即可） | A、B 和修订需要语言理解；接口不得写死到单一厂商 |
| 素材检索 | 按需求类型选用公开接口：文献用 Crossref，图片优先 Wikimedia Commons 等可标明来源与许可的来源，数据与事实以来源页为准 | 合法、可追溯；旧 SEAA 的 Crossref 发现逻辑可参考移植，不整包接入 |
| 下载与存储 | 工作目录落盘，记录 URL 与许可 | 满足可检查、可复现 |
| PPTX 生成 | `python-pptx` | 直接写原生可编辑元素；旧仓库中的探针可作为参考，不沿用其空壳输出方式 |
| 渲染预览 | LibreOffice 无头模式将 PPTX 转 PDF，再导出每页 PNG | 检查的是真实渲染结果，不是设计 JSON |
| 测试 | `pytest`，各阶段夹具 + 一次端到端真链 | 合同可单测；端到端不得用假外部资源或假模型输出冒充成功 |

V0.1 不引入学术 Deck IR、旧交接包格式，或设计资产数据库。页面设计用第 3.6 节的薄描述即可。若复用旧代码，只许移植独立函数（例如路径处理、Crossref 查询、python-pptx 画页），必须改到遵守本文契约。

## 5. 工程目录

新版本单独建目录或新分支空间，不在冻结的旧树里继续打补丁。建议结构：

```
ai-ppt-sys-v01/
  README.md
  docs/
    V0.1-总体开发任务书.md
    V0.1-技术方案.md          ← 本文
  contracts/                    # JSON Schema
  src/pptv01/
    cli.py                      # pptv01 "帮我做一个城市热岛效应的 PPT。"
    runner.py                   # 线性执行 A–H 与一次修订回流
    contracts.py
    a_plan/
    b_slide_plan/
    c_asset_requirements/
    d_retrieve/
    e_mapping/
    f_layout/
    g_pptx/
    h_qa/
  tests/
    test_a_plan.py
    test_b_does_not_lock.py
    test_revision.py
    test_contracts.py
    ...
  fixtures/                     # 仅用于合同与单元测试
  runs/                         # 每次真实运行的工作目录（可不入库）
```

一次运行的工作目录固定为：

```
runs/<run_id>/
  production_plan.json
  slide_plan.json
  asset_requirements.json
  asset_registry.json
  slide_asset_mapping.json
  page_design.json
  assets/
  previews/
  deck.pptx
  render/
  qa_report.json
  run_report.json
```

命令行只需要一句话作为入口。页数、结构、配色、具体素材都由系统自定，并在 `defaults_applied` 和修订日志里留痕。

## 6. 开发顺序

按任务书「先最短真链，再增强各环」执行。每一阶段结束时，必须留下真实输出样例和该阶段测试，再进入下一阶段。

1. **落地工程骨架**  
   建包、契约、工作目录约定、空 Runner 和 CLI。用一份手工填写的合法样例跑通读写，不接模型、不接网络。

2. **阶段 A**  
   实现一句话到 Production Plan。测试：能写出主题和约束；默认决策全部显式标注；不出现页数、页序、已写成结论的主张。

3. **阶段 B（只出暂定规划）**  
   实现研究简报和 Provisional Slide Plan。测试：每页有表达目标；`status` 必须是 `provisional`；不得把无来源的判断写成既定事实。

4. **阶段 C**  
   从暂定规划生成素材需求。测试：每条需求有页面、用途、合格标准；没有空洞的「配几张图」。

5. **阶段 D**  
   按需求真实检索和落盘。先打通一类（例如可许可图片或 Crossref 文献条目），再扩展类型。测试：登记含来源与许可；失败必须记为 `missing` 或进入替换，不得写假文件。

6. **修订回流**  
   主编根据 Registry 改 Slide Plan，必要时更新 C 并补取 D。测试：给一份缺关键素材或证据与初稿不符的登记，计划必须改，而不是原样通过。

7. **阶段 E**  
   绑定用途。测试：无关素材不能上页；未使用素材有说明。

8. **阶段 F**  
   按真实绑定做版式和预览。测试：设计只引用已绑定素材；允许因素材尺寸改排布，并留下说明。

9. **阶段 G**  
   写成可编辑 PPTX。测试：文件可打开；标题和正文是原生文本；图片为嵌入对象。

10. **阶段 H**  
    真实渲染并做基础检查，能定位的问题要修并复验。测试：人为制造溢出或缺图时能报出对应页。

11. **集中集成**  
    打通 CLI 真链。不得用 Mock 冒充真实外部资源或真实模型输出。单元测试夹具可以保留，但不得充当集成成功的证据。

12. **端到端验收**  
    输入不得预先指定页数、结构、配色或素材：

    > 帮我做一个城市热岛效应的 PPT。

    验收看七件事：是否理解需求；规划是否合理；素材是否真实、相关且绑定正确；版面是否基本可用；PPTX 是否完整、可编辑；质量在哪一环下降或失败；下一版先补什么。

## 7. 测试策略

- **合同测试**：所有 JSON 样例必须通过 Schema。
- **主编隔离测试**：见第 2.1 节两次验收，这是 V0.1 给 APC 留下的检测空间。
- **阶段测试**：每阶段用上一阶段的真实样例或合法夹具作为输入，检查本阶段输出。
- **端到端测试**：走真实检索和真实模型，产物全部保留。网络或许可失败时，报告应如实记录，并走修订或 `missing`，不能改写为成功。

---

## 8. V0.1 明确不做

- 复杂多 Agent 编排，以及把旧编排器改造成新主链。
- 与旧 APC 任务书、旧 Handoff、旧学术 Deck IR 的兼容层。
- 完整优秀 PPT 逆向解析、大规模模板库、通用 HTML/CSS 转 PPTX。
- 全自动学术审稿、声称经过同行级核验的结论。
- 为架构完整而增加、但与「先做出一份可检查 PPT」无关的基础设施。

这些可以在 V0.1 真链跑通、验收报告写出之后，再单独立项目。

---

## 9. 给实现的约束

- 改某一阶段的内部实现，只要输入输出仍符合本文契约，不应迫使其他阶段一起改。
- 任何默认决策、替换素材、自绘元素、改页或放弃某条需求，都必须写进对应 JSON，不能只留在模型对话里。
- 不把 Windows 绝对路径或本机目录写进代码，工作目录由 CLI 参数或环境变量给出。
- 不在日志或仓库中写入密钥。模型与检索密钥只来自环境变量。
- 旧仓库可参考，但新代码的合并目标是本方案的真链，而不是修补旧直线链路。
